== Introduction

[quote]
____
In racing, data is everything.

Data standards are how our devices talk to each other without making mistakes.
____

This Technical Library Standard (TLS) defines the rules for how data shall be 
handled within ODISC. 

Our system relies on many different parts working together. Track sensors 
need to talk to computers, computers need to update databases, and screens 
need to show live race stats.

Because these devices are made by different people and use different software, 
we need clear rules so that no messages get lost, mixed up, or delayed.

== Philosophy

We design our data rules around three simple ideas:

=== 1. Same Meaning, Different Formats
A piece of information, like a vehicle's number or a lap time, shall mean the 
exact same thing everywhere in the system. The information itself matters 
more than the format used to send it.

A race controller might send data as a tiny, fast numeric code, while a 
web browser displays it as text. No matter the format, the basic rules 
for the data shall stay the same.

=== 2. Check the Rules at Every Gate
In real-time racing, a single corrupted message can cause the system to miss 
a lap, display a wrong score, or crash the race screen. 

To prevent this, every device shall double-check incoming messages 
against the defined specifications. The system shall use defined error 
handling procedures to safeguard the process and prevent system crashes.

=== 3. Use the Right Tool for the Job
Different parts of the system have different limits. 

A decoder inside a vehicle needs to send data using as few bytes as possible 
to stay fast.

Meanwhile, a web page setup screen can use larger, easier-to-read text 
files. We create data rules that fit the job without making things harder than 
they need to be.

== Capabilities

To meet our goals, all specification documents shall support the following 
core capabilities:

=== 1. Universal Data Basics
The specification shall have a single set of rules for the absolute basics of data. 
This includes sharing the same rules across the entire system for text 
styles, how we name fields using standard uppercase and lowercase letters, 
and how we record dates and times.

=== 2. Readable Text Specifications
The specification shall support data formats that are easy for humans to 
read, write, and edit using a basic text editor. 

These text formats shall use strict, pre-defined rules to make sure they 
are valid before the system accepts them.

=== 3. High-Speed Hardware Formats
The specification shall support ultra-fast, compact data 
formats designed specifically for small hardware components 
and track communication.

These formats shall prioritize speed and low memory usage while keeping the exact 
same meanings as our readable text formats.
