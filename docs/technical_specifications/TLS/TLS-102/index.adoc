== Purpose

The global registry is the backbone of the ODISC system in that it
organizes and keeps track of identifications, implementations, track
designs and more that make up the ODISC ecosystem. The global registry
is the authoritative source of information that provides a mechanism for
updating existing tracks with firmware as well as sharing driver
profiles.

While connecting venues to the global registry is completely optional,
it provides the venue with multiple additional features via the shared
development that occurs on firmware.

The global registry also contains reference designs for various
implementations for components as well as racetrack build instructions
and definitions.

== Scope

This standard defines the architecture and responsibilities of the
global registry. We cover the philosophy behind our identity management
as well as data ownership. We also look at how synchronization of data
is handled, as well as how the ODISC global registry can be extended.

This document does not get into the details of implementation, and as
such database technology, communication protocols, authentication, user
interfaces, and similar items are all deemed to be out of scope and
referred to the detailed specification documents (Marked as DS-)
instead.

== Design Philosophy

The registry exists to improve the experience of using ODISC and is by
no means intended to restrict what you can do within the system. The
ODISC shall be fully operational without an internet connection,
although having it will provide benefits to both the venue and the
drivers.

The software that runs the global registry shall be released under an
open-source license to allow innovation and collaboration. Pull requests
from the community to add functionality that has an approved requirement
are accepted after review by the maintainers of the software.

== Architectural Role

The ODISC global registry is the single authoritative source for much of
the ecosystem. It enables distribution of updated firmware, driver
profiles, and provides a list of venues where racing occurs.

=== Global Shared Information

The global information includes the driver profiles, manufacturer
information and the hardware they have created for the ecosystem,
firmware, and more.

=== Venue Information

Each venue may have a profile that contains the location, facilities,
and similar details that are publicly available.

Private venues may choose to list their track with a "private" flag set
so that they don't get unexpected visitors, while still gaining the
benefits of being connected to the global registry for updates.

=== Racetrack Information

Each racetrack is linked to the venue it is at. This contains the track
layout, the certification level (updates over time), and similar data.
Since the shared systems that are configured at a venue have all this
information already, it can be automatically updated as things change
over time.

=== Race Results

Public venues have the option to share race results with the global
registry. Certain restrictions may be placed on this data transfer to
require track certification or competition levels (such as district or
above) or number of drivers that competed to reduce the risk of flooding
the database with excess information.

=== Local Information

While there is a lot of information that is shared with the global
registry, there is even more that instead kept locally.

This data is available via terminals and displays at the venue, and
while useful, are not needed at the global level. This allows venues to
keep local leaderboards of race results or fastest lap times current,
without requiring it to be shared with the world.

== Registry Domains

There are many types of data that we envision will end up in the global
registry. We touched on venues and racetracks earlier as well as
firmware, but we also see drivers, vehicles, and more being added as
well.

Please refer to the standards documents (DS-) for more information on
the exact types of data being stored, and how they are managed.

== Telemetry Definitions

Beyond the types of data mentioned as registry domains, we can also
store telemetry in the global registry.

Telemetry records are part of the race results and provide a mechanism
for running a ghost car on track that emulates the recorded race
session.

Telemetry records include throttle positions, lane changes, and timing
around the track to provide a repeatable vehicle path to race against.

== Identity Philosophy

The global registry is the definitive source for identity information.
Every registered identity shall receive a unique identifier that can be
used to retrieve records related to that identity from the registry.

Identity does not define implementation and does not change across
upgrades, unless the identity is used specifically to identify a version
of something. In that case, the identity provides the version and item
as a combined record, as opposed to just the item in question that has
its own identity.

_Example: +
A manufacturers implementation of a lane changer has an identifier. If
the manufacturer releases a new version of that same lane changer and
wants to track the version due to additional functionality, the lane
changer identifier remains the same, but there are two different version
identifiers._

This provides a persistent identity for all items, allowing the
ecosystem to query and identify all items connected to the system at a
racetrack. This allows the system to create an automated picture of what
the racetrack is as a monolithic definition.

Notice that the identity does not define implementation but rather
provides the needed support for interoperability between the various
systems that make up the ODISC system.

== Data Ownership

For any distributed system to work, there is one rule that must be
followed and the ODISC ecosystem is no different.

That rule is that every piece of data has one authoritative owner. Other
systems may cache the data, but only one system owns the true and final
determination of what that data is. Cached data can be referenced and
evaluated, but only the authoritative data can be used to determine the
final actual value of data. Any conflict is resolved by looking at the
authoritative source.

That said, there are situations where the owner changes such as when
race control submits a finished race package back to race scheduling to
record the results. When this occurs, the authoritative owner changes.
Put another way, race control is the authoritative voice over an ongoing
race, whereas race scheduling is the authoritative voice of races that
have already happened.

This key philosophy must influence all the downstream standards that
follow.

== REVIEW - Data Quality

Every Registry Object shall possess a defined level of trust that
reflects the confidence in the accuracy of its information.

Data Quality defines the confidence that consumers may place in Registry
Objects when making operational or competition decisions. It does not
indicate ownership or authority, only the degree to which the
information has been verified.

Suggested quality levels:

=== Level 1 — Authoritative

Information supplied or directly approved by the authoritative source
for that object.

Examples:

* Manufacturer specifications
* Official firmware releases
* Official racetrack reference definitions
* Certified competition rules

This represents the highest level of confidence.

=== Level 2 — Verified

Information submitted by users or organizations that has subsequently
been reviewed and approved by an appropriate authority.

Examples:

* Vehicle measurements verified by technical inspection
* Driver identity verified by a venue
* Certified venue information
* Competition inspection records

=== Level 3 — Community

Information supplied by users without independent verification.

Examples:

* Vehicle setup information
* Community supplied dimensions
* Suggested tuning values
* User maintained reference information

While useful, this information should not be relied upon where
verification is required.

== Synchronization Philosophy

Internet traffic is slow, while racing is not. For that reason, there
needs to be the ability to synchronize data from the global repository
down to the local installation, as well as the ability to return any
changes made back to the global repository.

For most items registration and creation can be done at the local level.
For some items, that feature may only be available at the global level.
This is determined on a case-by-case basis depending on the needs of the
system, and where it makes the most sense for someone to perform the
action.

By synchronizing data from the global repository to the local
installation, we enable the ODISC ecosystem to execute in an offline
mode. This removes the latency of internet operations from races as we
keep everything needed to run the system in a closed off circuit.

Because we are using asynchronous operations, there is a need for
conflict resolution. This may be implemented at a field level by
tracking the timestamp for each changed field, or it may be done at the
record level. Conflict detection and resolution are a must, and the
solution to that problem must provide a graceful recovery, potentially
asking the operator to choose what record to keep, or provide notice of
what was done to resolve the conflict.

The key takeaway here is that we need to be cognizant of issues that
will arise due to synchronization and do everything we can to limit the
impact of those issues. Both on the quality of the resulting data, as
well as on the users of the system.

== Version Management

To determine what items are compatible with each other, including
historically, we must use versioning of most items.

=== Standards versions

All documented standards must be given a version number.

=== Firmware versions

All firmware releases must have a version number that is interrogatable
by the bootloader, as well as a checksum.

=== Software versions

All software releases must have a version number associated with it.

=== Compatibility information

For the ODISC ecosystem to be able to self-validate, there needs to be a
versioned list of compatible items. This includes what software can be
used with which hardware reference implementations to work together, as
well as the firmware that is compatible.

=== Deprecation

Certain items may become obsolete, either due to updated standards that
they no longer meet, or that the manufacturer has decided to longer
produce that item. In these situations, there needs to be a way to mark
an item as deprecated in order for the ODISC ecosystem to alert the
track venues or other affected party of not only what is deprecated, but
also the reason and how to remedy it.

== Extensibility

At no point in time shall the global registry be considered a locked and
immutable item. Instead, it should be viewed as a living growing
collection of data related to how racing is done within the ODISC
ecosystem.

Changes to the global registry must be made in a manner that addresses
not only the new requirements, but also the need for both backward
compatibility and future standards. This same policy must also be
applied to any communication interface that is put in place for
transmitting data between the global registry and venue systems.

Not all data in the global registry shall be considered mandatory, as
there will be times when optional metadata or telemetry values are
collected. The goal here is interoperability with offline local
operations.

== Security Philosophy

Computer security is of utmost importance, and we do not take it
lightly. The ecosystem must be built in a manner that conveys trust in
the system. This is done via advanced authentication systems and robust
adherence to international laws and regulations such as the EU GDPR
doctrines. Privacy must be maintained and always respected.

The implementations and protocols must ensure authentication is done in
a manner that ensures data integrity and traceability. Consumers of the
global registry need to be able to trust that the data is valid and
authenticated.

All systems should operate based upon the lowest level of required
privileges to perform operations. If a system can be locked down by
providing an authenticated service instead of direct access to external
actors, that is a step worth taking.

== Registry Availability

At no point shall the lack of connectivity to the global registry
prevent local racing from taking place, if the racetrack has been
synchronized with the global registry during its original initialization
phase.

Local operations always take precedence over the global registry which
is there to provide improvements to the ecosystem. If the global
registry is not available, then the local system gracefully falls back
to a lower tier of interoperability without access to data in the global
registry.

== Future Directions

As mentioned earlier, we know that this global registry will grow.
Whether that is from the addition of shared ghost racing profiles,
public racetrack templates, or championship rankings with historical
statistics, we want to make room for them in a sound manner.

The goal here is that we want this to be expandable in the future,
because someone will come up with more ideas that make sense. Note that
the listed items are used as examples and are not commitments to
implement them immediately or in the next version.
