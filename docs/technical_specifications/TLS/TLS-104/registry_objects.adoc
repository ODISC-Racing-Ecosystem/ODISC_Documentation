=== Global Shared Information

The global information includes the driver profiles, manufacturer
information and the hardware they have created for the ecosystem,
firmware, and more.

=== Venue Information

Each venue may have a profile that contains the location, facilities,
and similar details that are publicly available.

Private venues may choose to list their track with a "private" flag set
so that they don't get unexpected visitors, while still gaining the
benefits of being connected to the global registry for updates.

=== Racetrack Information

Each racetrack is linked to the venue it is at. This contains the track
layout, the certification level (updates over time), and similar data.
Since the shared systems that are configured at a venue have all this
information already, it can be automatically updated as things change
over time.

=== Race Results

Public venues have the option to share race results with the global
registry. Certain restrictions may be placed on this data transfer to
require track certification or competition levels (such as district or
above) or number of drivers that competed to reduce the risk of flooding
the database with excess information.

=== Local Information

While there is a lot of information that is shared with the global
registry, there is even more that instead kept locally.

This data is available via terminals and displays at the venue, and
while useful, are not needed at the global level. This allows venues to
keep local leaderboards of race results or fastest lap times current,
without requiring it to be shared with the world.

=== Purpose

Defines the common principles governing all Registry Objects stored
within the Global Registry.

This standard establishes how Registry Objects are identified, owned,
versioned, related, synchronized, classified, and ultimately retired. It
provides the common information model that all downstream Domain
Standards shall follow.

=== Scope

This Domain Standard defines the common concepts that apply to all
Registry Objects within the ecosystem.

It establishes the lifecycle of Registry Objects together with the rules
governing identity, authority, ownership, relationships, metadata,
versioning, classification, synchronization, and extensibility.

This document intentionally does *not* define:

* Database schemas
* Storage technologies
* APIs
* Authentication mechanisms
* Communication protocols
* Synchronization algorithms

Those topics are defined within their respective standards.

=== Registry Object Philosophy

A Registry Object is any item that is tracked within the ecosystem.

Some Registry Objects represent physical items, while others represent
logical concepts, software releases, competition records, or
administrative information. Every Registry Object exists because it has
value to one or more systems within the ecosystem.

Examples of Registry Objects include, but are not limited to:

* Organization
** Venues
** Manufacturers
* Person
** Driver
** Venue Contact
** Manufacturer Contact
* Racetrack
** Reference Files (references document specification version)
** Venue Racetrack (references Venue and document specification version)
* Competition +
Competition-related Registry Objects contain numerous relationships to
other Registry Objects. Only the primary object types are listed here
for clarity.
** Race
** Race Session
** Race Result
* Vehicles
** Vehicle Model (references Manufacturer)
** Driver Vehicle (References Vehicle Model)
* Specifications and Implementations
** Document specification version
** Firmware (references document specification version)
** Software Release (references document specification version)
** Workshop Equipment Definition

Everything within the Competition domain contains numerous relationships
to other Registry Objects. For clarity, these relationships are
intentionally omitted from the examples above.

Registry Objects form the common language of the ecosystem. Every
subsystem exchanges information through Registry Objects rather than
implementation-specific data structures.

=== Registry Object Principles

Every Registry Object shall adhere to the following principles:

* Every Registry Object possesses one immutable identity.
* Every Registry Object has one authoritative owner at any given time.
* Authority and ownership are separate concepts.
* Registry Objects may reference other Registry Objects to reduce
duplication and improve consistency.
* Registry Objects evolve through versioning while preserving identity.
* Registry Objects should be retained whenever practical to preserve
historical information.
* Unknown Registry Object types shall not invalidate otherwise compliant
systems.
* Registry Objects synchronize between systems while preserving
identity, ownership, and authority.

These principles form the foundation upon which every Registry Object
definition within the ecosystem is built.

=== Localization - English as Default

The default language for all Registry Objects shall be English.

Localization may be applied to provide translated names, descriptions,
and other user-facing content in a user's preferred language without
changing the underlying Registry Object.

Localization shall never alter the identity, ownership, relationships,
or behavior of a Registry Object.

=== Identity

Every Registry Object shall be assigned a globally unique identity when
it is created.

This identity shall never be:

* Reused
* Duplicated
* Changed

Identity exists solely to uniquely identify a Registry Object. It is
independent of the object's purpose, ownership, name, or lifecycle.

Examples of similar identity systems include:

* UUID/GUID
* Hardware MAC Addresses
* Public Internet IP Addresses

While a Registry Object may evolve throughout its lifetime, its identity
remains constant.

=== Authority

Each registry object must define as part of its own specification the
following rules on how it operates. For authority, the who in question
refers to the application or larger system component/controller/function
that has the authority to execute these actions.

=== Who is allowed to create objects?

What systems are allowed to create new objects?

=== Who owns them?

What system is the owner of the records and responsible for ensuring
that all records are up to standard by applying validation rules to
records?

=== Who modifies them?

What system is allowed to modify records that are already in the
registry?

=== Who approves new or modified records?

What is the approval process for new records or modifications to
existing records? Is it automatic? Does it need approval from someone
with specific authority for the whole project, a manufacturer, a venue,
or maybe from a driver?

=== Can records be used before being approved?

If a user creates a new record, can they reference it before it is
approved by the appropriate approval process?

==== Approval Denied - What happens now?

What happens if a record is used and referenced before being approved,
and it is later denied approval?

=== User Permissions

For any objects that are created or modified due to user action, such as
on a website, can anyone perform the action? Or is it restricted to a
specific subset of authenticated users?

=== Conceptual Refresher

Authority determines permission.

Ownership determines responsibility.

These concepts intentionally remain separate throughout the ecosystem.

=== Ownership

Which system owns the record? At any given time, a given record may only
have one owner, but that owner may change as events occur.

Example:

* Venue Management owns the records that make up a scheduled race
* Prior to starting the race, the Venue Management transfers ownership
to Track Management system that now has control of the records
* The track management system, together with the various controllers
that are beneath it, records race events as they occur and adds them to
the race record.
* Once the race is completed and the race director finalizes the
results, the race record is returned to the Venue Management as a race
result.
* Venue Management owns the race result, although many actors can access
the race result to display data from it in various ways

This is the same object (race) during different stages of its lifecycle
that changes ownership as it is being processed and executed.

Ownership will generally only transfer when time sensitive or critical
events are occurring, and network latency is an issue for performance
and will impact the user or system experience negatively.

Ownership does not have to change just to edit data as editing the data
can be done by any system, but the final commit of that edit must be
done by the owning entity so that it can apply any validation rules to
ensure data quality.

Ownership identifies the system responsible for maintaining the
authoritative version of a Registry Object, while Authority defines
which systems are permitted to perform operations upon that object.

=== Object Lifecycle

Each registry record has a flag that identifies the current lifecycle of
that object. Think of this as an enumerated list of states that the
object can be in.

Lifecycle states:

* Proposed
** Used for items under review with a defined review process.
* Registered
** Used for items that are registered but have not yet been approved as
valid.
** Example: A driver is new at a venue and has registered to drive at
that venue but has not yet been approved by the venue as a driver.
* Reserved
** Used for items that are reserved for future use as a placeholder to
ensure certain functionality ends up in specific locations.
* Active
** A currently active record. Not much to say about this status. Most
items will live here.
* Deprecated
** These items have been replaced and superseded by another item of the
same type. Please use the new record or instance instead of this one as
it should no longer be used.
* Retired
** No longer in use. This may be a firmware that has been replaced by a
newer version. The old version isn't deprecated and can still be used,
but it has been retired and an upgrade is highly recommended.
* Archived
** For most record types, we do not delete data. Instead, it is flagged
as archived to remove it from search results or calculations. While it
is still possible to access or reference this data, there are most often
newer versions available of the same item.

=== Relationships

Very few repository items provide value without relationships to other
records. Each repository item specification must define any
relationships to other records, as well as if those relationships are
mandatory or optional.

Example: +
A vehicle has a manufacturer. Instead of typing this in every time, we
reference a manufacturer from the many that are already in the system. A
driver has a vehicle profile that references the vehicle as well as the
racetrack they race at with the settings contained in the profile (which
may vary by track). That vehicle profile may provide an optional link to
the decoder mounted in the car, as well as an optional link to the
preferred firmware for the decoder.

As you can see, relationships allow shared input of data, while
providing fast, efficient data input by reducing the amount of typing
needed to define things. If we know the decoder, we can limit the
options for the firmware selection to those that are valid for that
decoder.

=== Object Classification

Each registry object contains a classification, or object type.

Registry Object classifications are defined by their governing
specification. Downstream specifications should not duplicate this
information unless the classification itself forms part of the object's
meaning.

Classifications may include:

* Physical
* Logical
* Software
* Firmware
* Configuration
* Competition
* Administrative
* Reference
* Workshop

=== Metadata

Every registry object shall expose common metadata. These can be
considered the core of each record.

There are two types of metadata records, named and unnamed.

An unnamed record must expose the following metadata unless it is marked
as optional:

* Identity
** How do I find this record again?
* System Owner
** Which system component owns this record?
* User Owner
** If applicable, which user or user group owns this record?
** Example: Drivers own their driver record and only they can change it.
On the other hand, manufacturers also own their records but may allow a
group of users to edit and update them.
* Created and Modified timestamps
** These timestamps shall be recorded in UTC but can be displayed in
localized time zone formats.
* Version
** Optional: What is the version number for this item?
* Lifecycle/Status
** What is the current state of this object's lifecycle?

A named record must expose the following in addition to the requirements
of the unnamed record:

* Name
** Name of this record.
* Description
** Description of this record.

=== Versioning Principles

While objects may change over time, the identity identifier remains the
same throughout the life of the object. When new versions of an item are
released, a new version of an object may be derived from an existing
record to retain the data contained therein, but doing so must create a
new unique identifier.

=== Naming Principles

All names used in creating or defining a registry object shall be human
readable with an English naming convention. Should localization of an
object be desired, please see that section in this document for how to
resolve it.

Field names should prioritize readability over implementation-specific
naming conventions.

Example: Avoid Hungarian notation on fields (Example: Putting "s_" in
front of string fields) as this reduces readability

=== Registry Domains

Each registry object type is part of a domain. Each domain is owned by a
subsystem of the ecosystem.

This introduces a logical grouping of data and items that mostly follows
who owns, creates, and manages records.

Some example domains include:

* Drivers
* Organizations
* Venues
* Vehicles
* Software
* Hardware
* Competition
* Workshop
* Media
* Statistics

Please note that this list of domains still needs to be flushed out and
updated in a later revision of this document. Each registry object
definition document shall list the appropriate domain for that object in
the specification document.

=== Deletion and Retention

Objects generally aren't deleted but are instead Deprecated, Retired or
Archived. This preserves them for future use when it comes to statistics
and reporting.

=== GDPR

Human identifiable information must be wipeable by request so that the
personal information is no longer accessible. This does not require that
the records and historical data is removed, merely that any information
that identifies the individual is replaced by dummy data.

*Requirement:* Users shall acknowledge during registration that Registry
Objects synchronized to independently operated venues may remain stored
at those venues until synchronization or local administrative action
occurs. The Global Registry cannot directly remove or modify data stored
under the control of independently operated venues.

*Implementation Note:* The project's registration process and Terms of
Service shall address the legal implications of data synchronized to
independently operated venues, including appropriate legal protections
for the project regarding data that remains stored at venues outside the
project's administrative control.

_Example: Driver "John Doe" requests that his data is wiped. If the name
is the only personal data we keep for drivers, it can be replaced with
"Retired Driver #NNNN" where NNNN is a counter for how many drivers have
been wiped so far._

=== Extensibility

Future Registry Objects may be introduced.

Unknown object types shall not invalidate compliant systems.
